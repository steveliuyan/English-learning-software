# 决策记录 · UI 重设计轮图标呈现选型（2026-10-18）

## 背景

视觉稿定稿后，用户对图标单独提出诉求（原话）：

> 「那个图标的话，我还是拿不准。其实，我有点想要像扇贝一样的图标，就是有自己设计的图案在里面，
> 就有点像应用图标一样，而且还挺高级的」

这是一个纯视觉选型，不改界面结构，但它决定批 1 `ui/components/AppIcons.kt` 的工时与许可台账的措辞，
因此必须在批 1 开工前定下来。为此在视觉稿新增 §6.2「三案对照」：同一套造型骨架，
只差容器与内部层数，并配 44/48dp 入口块、30dp 行内退化行、深浅两套可现切。

现状基线（实测，非估算）：全仓库 `Icons.` 引用为 **0**，`ImageVector` 未使用，
图标全部是 Canvas 手绘——`AppBottomBar.kt` 11 处绘制调用、`WordCardScreen.kt` 4 处、
`CardDetailScreen.kt` 4 处、`CheckInScreen.kt` 2 处、`BackupPairingExportScreen.kt` 2 处，
另有 7 个 AI 功能用单个中文字（文 填 听 讲 析 拍 画）当徽标、设置页 3 个备份入口共用同一个 ⭕。

## 候选与选择

| 案 | 呈现 | 结论 |
| --- | --- | --- |
| A | 单色描边 + 域色 `deep` 实底容器，直接内嵌 Material Symbols 路径数据 | 落选。成本最低、33 屏最不会走样，但容器平色、图形只有一层，正是用户说的"不够高级" |
| B | **双色层次（duotone）**：描边骨架 + 内部半透明填充层，容器为域色渐变（`deep` → `deep` 混 35% `base`）+ 1px 内高光描边 | **采纳（用户 2026-10-18 选定）** |
| C | 图块化：48dp 渐变块 + 顶部高光条 + 极轻投影 + 实心图形 | 落选。行内 17dp 实心图形会糊，必须另做一族描边版；工时约 A 的 3–4 倍；深色下高光与投影须逐枚实测 |

选 B 的决定性理由：**"高级感"只存在于 ≥40dp 的容器上**。33 屏里绝大多数图标是列表行内的
30dp 容器 / 17dp 图形，在这个尺寸上三案会收敛成同一种样子（浅底 + 域色描边）。
B 让约 8–12 处大图块拿到渐变 + 双色的"图块感"，行内仍是描边，一套骨架两处通用；
C 则等于要维护两族字形。

## 硬约束：浅色 `base` 不得直接作白字形底

本节数字全部按 WCAG 2.x 相对亮度公式计算（`L = 0.2126R' + 0.7152G' + 0.0722B'`，
线性化阈值 0.04045 / 斜率 12.92 / 伽马 2.4），非估算：

- 白描边在浅色 `base` 上：**AI `#2EC99C` = 2.11:1**、**复习 `#FF9F0A` = 2.06:1**，
  低于非文本图形 3:1 的下限（WCAG 1.4.11）。薄荷与橙恰是最"好看"的两个域，最容易照抄 `base`。
- 白描边在浅色 `deep` 实底上：4.02:1（AI `#188F76`）~ 9.12:1（设置 `#48484A`），全部合格。
- 因此渐变容器的高光端取 **`deep` 混 35% `base`**（不是 `base` 本体），七域白描边实测 **3.17:1 ~ 6.26:1**，最差为 AI。
- 深色模式容器用同组域色（`deep = base`）配 `#06231A` 深色字形，实测 **5.96:1 ~ 9.82:1**，最差为危险 `#FF6B61`。

这条约束与选型无关，已写入 `docs/design/visual-style-guide.md` §2.3、§12 与设计规格 §2.1、§4.3、AC-R-03。

## 许可影响（选型带来的实际变化）

B 案的图形**不再复制 Material Symbols 的路径数据**，而是以它的 24dp 网格、2px 描边重量与 Outlined 风格
作为度量基准，逐枚自行绘制矢量路径。据此：

1. 台账条目 `material-symbols-icon-paths` 改述为「仅参考其度量与风格，本轮未内嵌其路径数据；
   若某枚图标确实直接内嵌上游路径数据，该条目对这一枚生效并须逐枚登记」。
2. 新增原创条目 `app-authored-ui-icons`：自绘 duotone 字形族，无第三方许可依赖、不产生署名义务、
   不引入新依赖（路径数据以 Kotlin 常量随 APK 打包）。逐枚清单钉在 `AppIcons.kt` 顶部注释，
   每新增一枚须同步该清单与本条「版本」字段。
3. `verifyThirdPartyNotices` 仍须通过（八字段非空），应用内许可页渲染同一份台账，无需改代码。

不引入 `androidx.compose.material.icons` extended 工件——`app/build.gradle.kts:163-165` 的
`dependencyLocking { lockAllConfigurations() }` 与本轮「不新增依赖」约束继续有效。

## 代价与验收

- 代价：批 1 图标部分工时约为 A 案的 1.6–2 倍（约 30 枚上下逐枚手写 `ImageVector`，每枚两层）；
  自绘族的风格统一要靠度量约束（同一 24dp 网格、同一描边重量、同一圆头处理）而非上游字形保证。
- 验收：
  - 每枚图标两层结构（描边骨架 + 内部半透明填充层），行内小尺寸退化为单层描边；
  - 容器渐变亮端为 `deep` 混 35% `base`，白描边 ≥3:1 由计算函数当场判（AC-R-03）；
  - 禁止 emoji、含字徽标、各处自绘异形图标继续存在（「AI」「♪」「⏰」全部替换）；
  - 深浅两套 + `fontScale 2.0` 下逐枚真机核验（AC-R-10 / AC-R-11）；
  - TalkBack 走查：有语义的图标按钮必须有真实读屏名，纯装饰图形 `contentDescription = null`（AC-R-12）。
