# 2026-11-10 原位译文覆盖（TATI）与悬浮窗屏幕翻译：管线选型与权限口径

用户当批要求（m06268，附一组开源项目清单）：
「一个是正常的拍照翻译，能在原位置上自动覆盖的译文；其二就是能做个悬浮窗，自动识别屏幕上的文字，然后来翻译」，
并明确效果形状：「检测文字框坐标 → 把原图原文抹掉（inpaint/背景填充）→ 在同一个位置、顺着原来排版画上译文，不是单纯把文字提取出来单独放一块」。

本仓已有拍照翻译（`ui/PhotoTranslationScreen.kt`、`phototranslation/PhotoTranslationUseCase.kt`、`language/domain/OcrProvider.kt`，
ML Kit 主路径 + Tesseract 降级），但出口只有「原文 / 译文对照」的文本列表。本决策只新增两条能力与它们的约束，
不改既有 OCR 分类与翻译失败分类的划分（spec 03 F3-03 的口径原样保留）。

## 1. 为什么不把那几个开源项目直接拿来当依赖

| 项目 | 语言/形态 | 结论 |
|---|---|---|
| Screen-Translator | Electron 桌面 | 只能当管线参考，不能进 Android 包 |
| Overlay-Translator | Android/Kotlin | 管线同构（检测→坐标→原位渲染），但其权限模型与依赖栈与本仓不一致，读代码思路即可 |
| Getup / MangaImageTranslator | Python + 重模型（inpaint） | 抹字做得最成熟，但形态是桌面批处理，权重体积与许可都未核验 |
| ImageTra | Python 工具包 | 同上，属后端思路 |

统一理由三条：①它们都不是本仓的 Kotlin/Compose 技术栈，硬接进来等于多一层进程间胶水；
②真正值钱的是**管线顺序**（检测 → 块坐标 → 翻译 → 擦除 → 原位重排），这套顺序我们已经能用自己的 OCR 块模型完整表达；
③重量级 inpaint 权重（LaMa 一类）的许可与本仓「未核验许可不得打包」的硬规则冲突（AGENTS.md），且体积预算没经过评估。
因此：**参考管线，不引入代码与权重**，并在 spec 03 许可门槛里写明这条边界。

## 2. 管线（本仓落地形状）

1. 相机/相册取图（既有 F3-03 入口）。
2. OCR 链路产出**块级结果**：每块带文本、包围盒、置信度、朝向。这是本轮唯一需要动既有契约的地方
   （现 `OcrRegion` 只有四个坐标 + confidence，没有块内文本），见第 3 节。
3. 一次请求翻译全屏块：上行是编号后的块文本数组，下行要求 JSON 数组 [{id, translation}]，
   **不传图片**。条数/id 校验在解析层做，不合格整批失败（AC3-08），个别 id 缺失时该块不覆盖、其余照画（AC3-09）。
4. 擦除原文：本轮用**背景取样填充**——取包围盒外扩一圈像素的中位数色铺满，并对边缘做 2px 羽化。
   明确取舍：这条路径在纯色/渐变背景（文档、网页、漫画天空）上肉眼过关，在纹理背景（照片、木纹）上会有补丁感。
   端侧 inpaint 网络列后续版本，启用前先过许可台账与体积预算。
5. 原位重排：字号由块高推得并钳制；按块宽折行；行高可向相邻块间隙借空间；仍放不下则截断加省略号，
   点按看全文；推导字号低于可读下限（11sp 等效像素）时**放弃该块覆盖**并标记「空间不足」，
   不做压扁到不可读的强行绘制（用户原话是要「顺着原来排版」，压扁就违背了这一点）。
6. 产物是新位图，三视图（原文 / 覆盖 / 上下对照）可切换，可保存与分享；原图字节不可变。

## 3. OCR 契约要升级成块级，而不是在 UI 层猜

现在 `OcrResult(text, regions)` 的 `regions` 只有矩形与置信度，块内文本丢了。原位覆盖必须知道「哪块矩形对应哪段文字」，
否则只能把整段文本摊到第一个矩形里，那是假覆盖。所以把契约升为 `OcrTextBlock(text, left, top, right, bottom, confidence, orientation)`，
`OcrResult` 同时保留整段 `text`（既有对照视图与历史记录仍用整段，不返工）。
ML Kit 的 `Text.Block` 天然给 `text` + `boundingBox`；Tesseract 侧用 PageIterator 的 block/para 级聚合拿词框并集。
两个 Provider 的映射都要有单测（块数、矩形单调性、文本拼接等于整段文本这三条不变量）。

## 4. 悬浮窗：为什么是 MediaProjection，而不是无障碍服务

| 方案 | 能拿到的 | 能不能原位覆盖 | 权限/合规 |
|---|---|---|---|
| AccessibilityService 读节点 | 只有文字树 | 拿不到像素位置，做不了原位覆盖，只能弹气泡 | 无障碍权限面向残障辅助，挪作屏幕翻译用途有滥用风险，商店审核口径不可控 |
| MediaProjection 截屏 | 真实像素 + 本机 OCR 块坐标 | 可以，且与 F3-04 共用同一套渲染 | 需用户授权；Android 14 起每次会话都要重新点一次 |

选 MediaProjection。三条必须照做的收敛：

- **截屏帧永不离开本机**：只在内存与短期临时目录，出站的只有文本，且逐次确认（沿用 F3-03 严于 F2-02 的口径，
  裁定仍归 `2026-11-05-ai-outbound-confirmation-granularity-and-network-security-config.md` D-1）。悬浮窗不因此获得任何「按域名一次」的豁免。
- **不假装长期免授权**：设计成「一次会话内持续翻译，直到用户停止」，前台服务 + 常驻通知可一键停止；
  授权撤销或项目被系统停止时自行清理并回到未启动态（AC3-13）。
- **成本与频率可见**：连续模式默认 3 秒节流 + 同屏指纹去重（同屏不重发，滚动/切页才重发），
  并在悬浮条上显示本会话已发请求数与模型名。

## 5. 与既有能力的关系

- 翻译仍走默认文本 Profile + `AiChatRequestBuilder` + `AiHttpTransport`，失败分类仍唯一由 `AiStatusFailure` 判定；不新增第二条 AI 通路。
- OCR 不可用（无 GMS 且 Tesseract 模型缺失）仍报「OCR 不可用」，不得落成翻译失败（AC3-04 不变）。
- 覆盖与悬浮窗都不写学习事件、不改今日计划、不动词书资产。

## 6. 已知风险

1. 背景取样填充在纹理背景上有补丁感——这是本轮明确接受的取舍，界面需在覆盖视图上给「效果受限」提示而非假装完美。
2. MediaProjection 在部分 OEM（含本机 M2102J2SC）上被省电策略杀项目，需前台服务 + 通知，真机走查必测。
3. 中英混排与竖排文字的重排质量在第一版会明显弱于横排英文；竖排先统一横排缩排处理，并在 spec 里写明。
4. 一屏块数过多（比如密集列表）时，单次请求的 token 量会不小，成本提示必须按实际块数与字符数估算。
