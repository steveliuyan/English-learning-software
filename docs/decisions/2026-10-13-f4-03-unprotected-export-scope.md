# 2026-10-13 F4-03 无认证 Salvage 导出范围裁决

## 背景

`docs/superpowers/specs/2026-10-11-logical-backup-export-design.md` 第 8 行与"范围"节规定：在迁移认证/签名能力接入前，不向用户开放正式备份导出、不把未签名文件称为备份；容器仅在测试中使用合成数据。

F4-03（Spec 04）要求备份导出接真实数据并提供用户可见的导出入口，两者存在直接冲突。F4-04（配对认证、签名、加密、恢复）是后续独立阶段，依赖 F4-03 的数据组装与格式。

## 候选方案

1. **维持原门槛**：F4-03 只做内部数据组装与格式，不开放 UI 导出，等 F4-04 签名完成后一起放开。缺点是用户数据链路长期无真实验证，F4-04 被迫串联过大范围。
2. **开放"无认证 Salvage 包"导出（本次采纳）**：F4-03 接入真实数据并开放 SAF 导出，但产物明确定位为"应急数据保全包"（salvage），不是可认证恢复备份。
3. 推迟 F4-03 到 F4-04 之后：违背 Spec 编号依赖（F4-04 依赖 F4-03 的包内容），不可行。

## 决定（用户已批准，2026-10-13 主会话）

采纳方案 2，附带以下强制约束：

- manifest 的签名状态如实标记为 `not-protected`，认证与加密元数据只允许占位值，不得伪装已签名或已认证。
- UI 文案必须明确："当前包不可用于认证恢复，F4-04 完成后才支持恢复"；任何界面、manifest、日志不得称其为"已认证备份"或"可恢复备份"。
- 摘要（SHA-256）仅用于发现意外字节损坏，不构成真实性保证；不得用无密钥哈希冒充签名。
- F4-04 完成认证与恢复协议后，才允许把该包宣传为"可用于换机恢复"；恢复端在认证实现前拒绝此类包属于预期行为。
- 设计文档 `2026-10-11-logical-backup-export-design.md` 状态行同步更新，指向本裁决。

## 影响

- F4-03 范围与 Spec 04 文字保持一致，仅解锁"接真实数据 + SAF 导出入口"这一原设计文档的内部限制。
- 新增决策不改变 F4-04 的验收标准：AC4-04/05/06 仍要求一次性配对挑战、签名覆盖验证、fail-closed 恢复，Salvage 包不满足 F4-04 前置即为不可恢复，这是如实状态而非缺陷。
- 用户换机数据保全能力提前可用（手动导出的价值：防卸载/清数据丢失），与 AGENTS.md"本地优先、无隐式云同步、用户自行妥善保存备份"的定位一致。
